# Enterprise Know-How Benchmark 技术报告

[English](REPORT.md) · 简体中文 · [项目主页](../README.zh-CN.md) · [公开题库](../tasks/README.md) · [运行与评分指南](../tasks/RUN.md)

Enterprise Know-How Benchmark 评测语言模型 Agent 在执行跨软件、重业务判断且包含老旧业务系统的真实企业工作流时，能否在不可撤回的首份正式交付中准确执行公司内部的岗位规程（Institutional Know-How）。评测横跨真实桌面跨软件环境与确定性老旧 ERP 命令行工作台，固定执行模型、可用工具与单据输入，仅改变运行时的程序性知识条件：只给上一班次历史结案记录的基线（Arm A）、补充由 [Lynx Cognition](https://enterprise.lynxai.work) 从早期操作示范中蒸馏出的工作流 Skill（Arm B 使用 `GLM-5.3`，Arm C 使用 `DeepSeek Flash`），以及直接提供完整公司书面制度原文的上界对照（Arm D）。

跨软件运行环境基于 [TheAgentCompany](https://github.com/TheAgentCompany/TheAgentCompany)（[Xu et al., 2024](https://arxiv.org/abs/2412.14161)）的自托管企业服务栈构建，包含固定镜像摘要的 `ownCloud`、`Rocket.Chat` 及可选 NPC 服务，配合原生桌面浏览器与电子表格软件执行。本报告全部统计均以预定完整批次中接收方收到的首份正式交付为准，完整保留持平样本、未完结账本、软件崩溃及分数回退。

## 核心结论

1. **仅凭少量历史结案记录无法覆盖企业规则边界。** 在只提供当前单据和上一班次历史记录的条件下，`gpt-6.1-terra`（`high` 推理档）在 40 张原生 Chrome 财务交接单上的首交全对率为 **24/40（60.0%）**，在 16 张模拟 ERP 双发票汇款单上的全对率为 **0/16（0.0%）**，其中 32 行汇款明细有 19 行被转交人工，并在应付审核中出现向未完成核验的新银行账户直接放款（`AP-1026`）。
2. **示范蒸馏 Skill 在规则密集型交接任务上追平完整制度原文，并可跨界面迁移。** 注入 `GLM-5.3` 蒸馏 Skill 后，40 张原生财务工单首交全对率从 **24/40 升至 40/40（100.0%）**，单次会话耗时中位数基本不变（应收 `148s → 150s`，应付 `157s → 147s`）。在预定同题对照子集上，`DeepSeek Flash` Skill（Arm C，20 题）与直接给制度原文的 Arm D（10 题）均取得 **100.00**。将从单票 Chrome 示范蒸馏出的同一份应收 Skill 直接用于模拟 ERP CLI 双发票核销，业务均分从 **28.13 升至 94.84**（`GLM-5.3`，13/16 全对）和 **100.00**（`DeepSeek Flash`，16/16 全对）。
3. **蒸馏模型选择与人工审阅在细粒度残差边界上存在可测差异。** 在 6 组配对实验中，两款蒸馏模型均优于无 Skill 基线。未经审阅的 `DeepSeek Flash` 原始审批候选 Skill 在两轮共 32 次执行中得 **30/32（93.75%）**（首轮出现 1 次误放行与 1 次转人工）；经过 [Lynx Cognition](https://enterprise.lynxai.work) 标准产品审阅流程后，两款模型均达到 **32/32（100.0%）**。而在双发票尾差处理上，`DeepSeek Flash` 在 `RMT-765`、`RMT-786`、`RMT-793` 三单上均得满分，优于将小额尾差留在催收的 `GLM-5.3`（均得 `72.5`）。
4. **程序性 Know-How 存在两条明确边界：大规模组合消歧与原生桌面软件稳定性。** 在两张各含 108 笔发票、经独立验证器证明存在唯一全局解但禁用外部脚本求解器的月结银行锁箱（`lockbox-month-11`、`lockbox-month-23`）上，三组全部停在 **54/108（50.00%）** 和 **57/108（52.78%）**。在需重算 8 组状态共 384 个公式单元格的银行拒付工作簿（`cb-17`、`cb-28`）上，允许本地 Python 与表格工具生成文件时三组全部通过（**384/384**）；改走原生 `LibreOffice Calc` 图形界面操作后，6 次会话均发生 2 至 3 次软件崩溃，基线组出现崩溃恢复跨场残留异常，`GLM-5.3` 组在 `cb-17` 上提交了无公式静态文件（`0/384`）。此外，在原生月结现金批次 `close-118` 中，`GLM-5.3` 因单笔折扣计算偏差 `SGD 0.50` 从基线的 `100.00` 回退至 `91.25`。

## 1. 研究背景与同类基准对比

现有办公与桌面评测表明，通用模型在软件工程之外的企业运营任务上表现明显偏弱。在 [TheAgentCompany](https://github.com/TheAgentCompany/TheAgentCompany)（[Xu et al., 2024](https://arxiv.org/abs/2412.14161)）覆盖的多部门自托管办公任务中，财务（Finance）与行政（Admin）岗位的完成率处于最低区间。同期相关基准各自切入不同层面：[OSWorld](https://arxiv.org/abs/2404.07972) 侧重原生操作系统图形界面交互，[$\tau$-bench](https://github.com/sierra-research/tau-bench) 与 [CRMArena-Pro](https://arxiv.org/abs/2505.18878) 评测客服与 CRM API 下的规则遵循，[SkillsBench](https://arxiv.org/abs/2602.12670) 测量容器化任务挂载过程性知识模块后的通过率变化。

在实际企业交接场景中，接手队列的操作员既不是面对空白环境，也很少拿到实时维护的完备手册，常见输入是待办单据与上一班次留下的若干历史结案记录。此时模型失误通常来自三类不同原因：

1. **缺少公司隐性规程（Institutional Know-How）**：有限的历史结案样本不足以唯一推导出公司内部阈值，例如金额与比例双上限销账规则、已入账贷项通知单是否扣减现金折扣基数、银行起息日宽限期，或越权及过期豁免批件的处理方式。
2. **首交不可撤回的业务风险**：在资金放行与应收核销岗位上，发往财务队列的首条正式指令会直接触发后续动作。遇到边界情形一律转人工会阻塞账期，盲目放行则会造成资金违规流出或超额折让。允许反复试错后只看最终状态的判分方式会掩盖此类运营风险。
3. **任务本身的结构性上限**：即便操作员完全掌握业务规则，当任务需要在无求解器条件下完成跨全账本的组合消歧，或依赖易崩溃的原生桌面电子表格维持复杂公式时，单靠程序性规则仍无法稳定完结。

Enterprise Know-How Benchmark 通过固定同一执行模型、同时保留原生桌面与模拟 ERP CLI 两种执行面、严格按首份正式交付判分，并将规则交接主集与边界压力测试集并列发布，将上述三类因素逐一拆开测量。

## 2. 实验环境、任务设计与评测协议

### 2.1 运行界面与软硬件环境

已发布实验统一在隔离的 `arm64` macOS 26.4（`25E246`）宿主机上执行，使用 `codex-cli 0.169.0`、Python `3.12.16`，固定执行模型为 `gpt-6.1-terra`（`high` 推理档，完整记录见 [environment.json](environment.json)）。任务运行于两类界面：

* **原生跨软件桌面环境**：复用 [TheAgentCompany](https://github.com/TheAgentCompany/TheAgentCompany) 的容器化 `ownCloud 10.0.10` 与 `Rocket.Chat 5.3` 服务（固定镜像摘要）。每次试验创建独立的私有房间与文档目录；操作员通过原生 Google Chrome（`158.0.8127.37`）新建 Guest 窗口（财务单票限时 600 秒，工作簿限时 900 秒）查阅当期凭据与上期交接记录，并向财务房间发送正式结论。电子表格批次同时调用原生 `LibreOffice Calc` 或 `Apple Numbers`。
* **模拟老旧 ERP 工作台**：模拟企业内部缺少现代 API 与脚本控制台的传统终端过账工作台（仅提供 `./work read`、`./work submit`），单次会话限时 300 秒。工作台提供合成账本、历史过账记录、缺失电子发票号的历史遗留回单（Legacy Remittances）、候选匹配三元组或带手写涂改的月台签收扫描图（`PNG`），接收首份提交后立即锁定并返回 SHA-256 回执。

### 2.2 四组配对实验条件

每道预定工单在各实验组均使用全新目录与独立模型会话，题面、工具与业务单据完全一致：

| 组别 | 实验条件 | 运行时向操作员提供的资料 |
|---|---|---|
| **A** | 仅历史记录（基线） | 当期工单凭据或账本记录，以及上一班次已结案历史工单 |
| **B** | Lynx Cognition（`GLM-5.3`）蒸馏 Skill | Arm A 全部资料，加上由 [Lynx Cognition](https://enterprise.lynxai.work) 使用 `GLM-5.3` 从早期操作示范蒸馏的冻结工作流 Skill |
| **C** | Lynx Cognition（`DeepSeek Flash`）蒸馏 Skill | Arm A 全部资料，加上同样由 [Lynx Cognition](https://enterprise.lynxai.work) 使用 `DeepSeek Flash` 从同一批示范蒸馏的冻结工作流 Skill |
| **D** | 制度原文对照（Oracle） | Arm A 全部资料，加上出题所依据的完整公司书面制度原文 |

Arm B 与 Arm C 使用的工作流 Skill 在评测开始前由 [Lynx Cognition](https://enterprise.lynxai.work) 采集早期原生操作示范并编译冻结；除标明 `raw`（未审阅候选）的消融行外，两款蒸馏管线的编辑阶段统一使用 `DeepSeek Flash`。全部评测工单均与训练示范隔离，Skill 内不包含题目答案或评分逻辑。

### 2.3 首份交付确定性评分

* **应收核销评分（每张发票 0–100 分）**：现金折扣与转理赔金额完全正确得 35 分，销账金额与剩余应收余额完全正确得 35 分，后续跟进责任方正确得 20 分，四项金额勾稽对平得 10 分。多发票单据取各行均分，全对要求每行均得 100 分。
* **应付审核评分（每张发票 0 或 100 分）**：放行或暂扣决定正确，且列齐全部适用暂扣原因代码方可得 100 分，缺漏或多报原因计 0 分。
* **协议约束**：重复发言、修改已发消息、重复或未分配发票号、超时及异常退出均计 0 分。原生 Chrome 批次同时公布按财务接收日志判定的**业务分**，以及将任何缺少 Guest 窗口关闭证据或轨迹异常会话直接计零的**严格协议分**。

## 3. 主实验结果：跨软件财务交接与跨界面迁移

### 3.1 原生跨软件财务交接（40 单，110 次独立会话）

主批次包含 40 张未见工单（24 张应收短付核销、16 张应付放行审核）与 110 个独立会话（40 对 A/B 主配对、20 次 Arm C 对照、10 次 Arm D 对照）。逐单明细见 [finance.md](finance.md) 与 [finance-scores.csv](finance-scores.csv)。

合并全部 40 单，业务均分从 Arm A 的 **72.50** 升至 Arm B 的 **100.00**，首交全对率从 **24/40（60.0%）** 升至 **40/40（100.0%）**（提升 `+40.0` 个百分点，16 单提高、24 单持平、0 单下降）。40 张工单按 10 条正交业务规则构造（每条规则 4 单）：

| 考查的业务规则边界 | 岗位 | 工单数 | Arm A（无 Skill） | Arm B（`GLM-5.3` Skill） | 分差 | 提高 / 持平 / 下降 |
|---|---|---:|---:|---:|---:|---|
| 已入账贷项与核销基数 | 应收 | 4 | 47.50 | 100.00 | +52.50 | 3 / 1 / 0 |
| 多个独立付款门禁同时触发 | 应付 | 4 | 50.00 | 100.00 | +50.00 | 2 / 2 / 0 |
| 银行宽限期与付款指令时点 | 应收 | 4 | 55.00 | 100.00 | +45.00 | 3 / 1 / 0 |
| 销账绝对金额与比例双上限 | 应收 | 4 | 72.50 | 100.00 | +27.50 | 2 / 2 / 0 |
| 现金折扣基数及上限 | 应收 | 4 | 72.50 | 100.00 | +27.50 | 2 / 2 / 0 |
| 豁免范围、审批权限与有效期 | 应付 | 4 | 75.00 | 100.00 | +25.00 | 1 / 3 / 0 |
| 新收款银行账户与核验记录 | 应付 | 4 | 75.00 | 100.00 | +25.00 | 1 / 3 / 0 |
| 运单匹配与签收凭据（POD） | 应收 | 4 | 82.50 | 100.00 | +17.50 | 1 / 3 / 0 |
| 转入理赔金额上限 | 应收 | 4 | 95.00 | 100.00 | +5.00 | 1 / 3 / 0 |
| 解除暂扣的权限与事件先后顺序 | 应付 | 4 | 100.00 | 100.00 | +0.00 | 0 / 4 / 0 |

增益并非集中于单一规则：每次剔除任意一组应收规则后，其余工单均分增益仍保持在 `+24.50` 至 `+34.00`；每次剔除任意一组应付规则后，其余工单增益保持在 `+16.67` 至 `+33.33`。

**首份交付的具体变化：**
* *消除保守转人工与尾差误判（`ar-22711` / 发票 `I-22711`）*：无 Skill 基线无法仅从上期样本确认已入账贷项后 `OTHER` 类尾差的销账口径，首交 `REFER I-22711: SGD 4.76 remains after cash and posted credit; prior examples do not establish write-off treatment for this OTHER-labelled residual.`（得 `0` 分）；使用 Skill 后首交 `I-22711,0.00,0.00,0.00,4.76,COLLECTIONS`（得 `100` 分）。
* *拦截违规放款（`AP-1026` 与 `INV-15427`）*：当发票金额无误但收款方新银行账户尚未完成核验或存在多重门禁时，Arm A 直接提交放行指令（`RELEASE,NONE`，得 `0` 分），Arm B 则准确挂起并给出完整原因代码（`HOLD,BANK_UNVERIFIED`，得 `100` 分；见 [AP-1026 操作记录](cases/AP-1026/history.json)）。

**运营风险、严格浏览器核验与执行耗时：**
* 人工转交从 Arm A 的 `4` 单（应收 1、应付 3）降至 `0`；应收超额折让从 `1` 降至 `0`；应付错误放行从 `1` 降至 `0`。
* 自动原生浏览器协议核验在应收上通过 `23/24`（Arm A）与 `22/24`（Arm B），在应付上均为 `16/16`。若将未通过浏览器核验的试次计零，应收均分仍从 **66.67 升至 91.67**（两侧均通过核验的 21 对样本平均提升 `+33.33`），应付均分从 **75.00 升至 100.00**。
* 单次试验耗时中位数几乎不变：应收为 **148 秒 → 150 秒**，应付为 **157 秒 → 147 秒**。

### 3.2 跨界面迁移：模拟 ERP 双发票汇款核销（16 单，48 次会话）

为检验从单票原生浏览器示范中提取的规则能否直接迁移至不同工具界面与多票组合结构，实验将同一份冻结应收 Skill 原样投入模拟 ERP CLI 的 16 张双发票汇款单（见 [remittances.md](remittances.md) 与 [remittance-distillers-20261119](batches/remittance-distillers-20261119/README.md)）：

* **Arm A（仅历史记录）**：业务均分 **28.13**，双行全对 **0/16**，单行全对 **6/32**，11 张汇款单共 **19/32** 行明细被转交人工复核。
* **Arm B（`GLM-5.3` Skill）**：业务均分 **94.84**（`+66.72`），双行全对 **13/16**，单行全对 **29/32**，人工转交降至 **0/32**；15 单提分、1 单持平（`RMT-765` 均为 `72.5`）。

## 4. 对照与消融：制度原文、蒸馏模型选择与审阅环节

### 4.1 蒸馏 Know-How 与完整书面制度原文对比（Arm D）

在预先排定的 10 张原生财务工单（6 张应收、4 张应付）上，Arm D 直接向操作员提供公司书面制度原文。Arm D 在应收与应付上均取得 **100.00**，与 Arm B（`100.00`）完全一致（分差 `+0.00`）。在历史 16 单应付审批两轮对照（每组 32 次会话）中，附完整制度组同样取得 **32/32（100.0%）**，与审阅后的蒸馏 Skill 持平。这表明在被测规则集上，从历史示范蒸馏出的 Skill 达到了与直接提供现成书面制度同等的首交决策精度。

### 4.2 `GLM-5.3` 与 `DeepSeek Flash` 蒸馏对比及审阅消融

[distillers.md](distillers.md) 与 [distiller-scores.csv](distiller-scores.csv) 汇总了两款蒸馏模型在同一批示范上的对比结果：

* **原生财务同题抽测（20 单）**：两款蒸馏模型在 12 张应收与 8 张应付工单上均得 **100.00**（基线均分 `79.75`）。在基线未满分的 6 张工单（`ar-23951`、`ar-21731`、`ar-26437`、`ar-22803`、`ar-23217`、`ap-1026`）上，两者提分幅度逐单完全相同（应收平均 `+61.00`，应付 `+100.00`）。
* **原生短付确认小样本（4 单）**：基线均分 `43.75`，`GLM-5.3` 为 `86.25`，`DeepSeek Flash` 为 `100.00`（差异来自 [I-7547](cases/I-7547/history.json)：三组依次为 `30`、`45`、`100`）。
* **双发票小额尾差结清（16 单 ERP）**：在 `RMT-765`、`RMT-786`、`RMT-793` 三单上，`GLM-5.3` Skill 将其中一笔应予结清的小额尾差留在了 `COLLECTIONS`，单题均得 `72.5`；`DeepSeek Flash` 完整覆盖该边界，三单均得 `100.0`。
* **冻结前产品审阅的作用（32 次 ERP 付款审批会话）**：直接使用未经审阅的原始蒸馏产物（`raw`）时，基线为 `25/32（78.13%）`，`GLM-5.3` 为 `32/32（100.00%）`，`DeepSeek Flash` 为 `30/32（93.75%）`（首轮在均需因账户未核验暂扣的 `INV-8259` 和 `INV-8350` 上分别出现放行和转人工）。经过标准产品审阅修订后，`DeepSeek Flash` 同样升至 `32/32（100.00%）`。

## 5. 关账压力测试与能力边界（Know-How 在哪里失效）

后续冻结批次（[close-workflows.md](close-workflows.md)）进一步测试了跨往来方抵销、截账时点外部依赖、月台签收图像核验、大规模锁箱组合匹配与公式驱动工作簿。所有预定批次完整公布，不剔除天花板效应或负向回退样本。

### 5.1 跨账本联动抵销与截账挂起（Know-How 有效区间）

* **AR/AP 联合关账（[joint-close-20261119](batches/joint-close-20261119/README.md)）**：`net-31` 与 `net-42` 两个班次各含 8 家往来方、24 条评分指令，应收核销金额一旦算错会直接传导至应付敞口及法定抵销暂扣原因。Arm A 分别得 `28.33`（`5/24` 全对）与 `72.29`（`10/24` 全对），均分 **50.31**；`GLM-5.3` 与 `DeepSeek Flash` 在两个班次上均取得 **100.00（48/48 全对）**。
* **17:00 截账未决依赖（[cutoff-20261119](batches/cutoff-20261119/README.md)）**：`cutoff-19` 与 `cutoff-27` 共 16 笔发票，其中 11 笔凭据齐备可入账，另有 5 笔受制于已签署的外部未决事项（共用未拆分银行回单、银行查证在途、贷项通知单编号截断）。Arm A 在截账前仅正确入账 **2/16（12.50%）**，处置均分 **62.19**。两款蒸馏 Skill 均将全部 **11/16（68.75%）** 可执行发票准确入账（达到当前证据允许的自动化上限），并将全部 5 笔外部阻塞单据挂起至对应责任方（`WAIT`），处置分均达 **100.00**，且无一例违规强行入账。
* **月台签收扫描件核赔（[pod-inspection-20261119](batches/pod-inspection-20261119/README.md)）**：在包含 60 个托盘货位标记与 4 条主管手写修正的 `pod-47`、`pod-83` 上，三组均得 **100.00**，表明该版式下的多模态图表读取本身不构成基础模型的瓶颈。

### 5.2 边界一：大规模银行锁箱中的全局组合消歧

银行锁箱任务中，ERP 已预先列出每笔银行回单在金额上局部配平的全部三发票组合，操作员需在 300 秒内仅用工作台读写命令（无脚本控制台或外部求解器）提交全局互不重叠的发票分配方案。

* **12 笔回单班次（[lockbox-20261119](batches/lockbox-20261119/README.md)，每班次 36 笔发票）**：在 `lockbox-76`（120 个局部候选三元组）上三组均完成 `36/36`；在 `lockbox-41`（142 个候选三元组）上，Arm A 与 `DeepSeek Flash` 仅匹配 `9/36（25.0%）`，`GLM-5.3` 完成 `36/36（100.0%）`。
* **36 笔回单月结班次（[monthly-lockbox-20261119](batches/monthly-lockbox-20261119/README.md)，每班次 108 笔发票）**：`lockbox-month-11` 与 `lockbox-month-23` 各含 18 笔带电子发票号的 EDI 回单与 18 笔无发票号历史格式回单（局部合法三元组分别达 `241` 与 `243` 个）。独立验证器（[verify_lockbox.py](../evaluation/verify_lockbox.py)）枚举证明每张账本恰有唯一完整解。然而**三组在两个班次上全部未能完结**，一致停在 **54/108（50.00%）** 与 **57/108（52.78%）**。Skill 改善了风险控制（在 `lockbox-month-23` 上两款 Skill 均将剩余 17 笔歧义回单安全转人工，而无 Skill 基线额外提交了一组错误分配），但自然语言程序性规程无法在无求解器环境下替代大规模组合搜索。

### 5.3 边界二：原生图形界面电子表格崩溃与负向回退

* **本地代码生成 vs. 原生 LibreOffice Calc（[chargeback-office-20261119](batches/chargeback-office-20261119/README.md) vs. [chargeback-native-20261119](batches/chargeback-native-20261119/README.md)）**：`cb-17` 与 `cb-28` 要求构建在 8 组银行事件流重放状态下均可自动重算的拒付核算表（每态 48 项，共 `384` 项公式检查，限时 900 秒）。当允许使用本地 Python（`openpyxl`）与脚本工具时，**三组在两份模板上全部取得 384/384（6/6 份全过）**。而限定必须通过原生 `LibreOffice Calc` 编辑、经 `ownCloud` 上传并在 `Rocket.Chat` 交付时：
  * 全部 6 次正式会话中 `LibreOffice Calc` 均记录到 2 至 3 次进程崩溃。
  * 在 `cb-28` 上，Arm A、`GLM-5.3`、`DeepSeek Flash` 首交得分依次降至 **0/384（0.00%）**、**140/384（36.46%）** 与 **162/384（42.19%）**；其中 Arm A 在 Calc 崩溃恢复界面曾短暂弹出上一场试验残留模板并由操作员关闭（已记录为环境隔离异常）。
  * 在 `cb-17` 上，Arm A 与 `DeepSeek Flash` 取得 **384/384**，而 `GLM-5.3` 提交的工作簿输出区缺少可重算公式，得 **0/384**。
  * 早期在 `Apple Numbers → ownCloud → Rocket.Chat` 上的历史对照（[workbook-trials.json](workbook-trials.json)）同样呈现桌面软件瓶颈：Arm A 与 Arm B 各完成 **1/2**（Arm B 遇 Numbers 卡死未交付，Arm A 导出时丢失半数公式）。
* **原生月结现金核销中的单题回退（[month-end-20261119](batches/month-end-20261119/README.md)）**：在 `close-204` 上三组均得 `100.00`；在 `close-118` 上，Arm A 与 `DeepSeek Flash` 均得 `100.00`（`8/8` 票全对），而 `GLM-5.3` 在 `I-7180` 一票上将现金折扣 `SGD 8.16` 误算为 `7.66`，总分回退至 **91.25**（`7/8` 票全对，且严格轨迹检查未确认 Guest 窗口关闭）。

## 6. 局限性与适用范围

1. **单一固定执行模型**：现有正式对照固定使用 `gpt-6.1-terra`（`high` 推理档）以控制执行端变量。更换能力更强或更弱的基础模型、或改用不同 Agent 框架时，基线水平与 Skill 边际收益可能变化；公开执行器支持通过 `--model` 与 `--agent` 直接接入其他系统复测。
2. **领域聚焦与合成账本**：题库集中在应收、应付、采购询价与月结关账等规则密集型后台流程，并使用按真实会计控制边界构造的合成单据，以便在不暴露企业真实客户隐私的前提下公开完整标准答案、多状态重放测试与原始回执。
3. **压力测试批次样本量**：主实验（原生财务 40 单共 110 会话、双发票 16 单共 48 会话、应付审批每组 32 会话）具备多工单统计分母；后续关账与原生工作簿压力测试采用每类工作流 2 个班次或模板（每组每题 1 次独立会话），主要用于定位结构性失效机制。
